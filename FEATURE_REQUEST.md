# Feature request: task history

We need an audit trail for tasks. Every time a task is updated (status, priority, assignee, due date, title, description), we want a history row capturing **what changed, when, and to whom it was assigned at the time**.

## Must-have

- A history row is written for every change made via `PUT /api/tasks/{id}`
- A history row is written when a task is created (`POST /api/tasks`)
- A history row is written when a task is deleted (`DELETE /api/tasks/{id}`)
- `GET /api/tasks/{id}/history` returns the history for a task, newest first

## Constraints

- Don't break any existing endpoint or test (`mvn test` must stay green for the existing 19)
- Use the existing patterns (CLAUDE.md describes them)
- No new dependencies in `pom.xml`

## Deliberately left to your judgement

- Schema for "what changed" (a JSON column? individual columns? a `change_summary` string?)
- Whether you store the entire task snapshot or just the diff
- How to handle history for already-deleted tasks
- Pagination strategy for tasks with many updates

## How this exercise is graded

This is the **prompting-tactics** exercise. The point is not just to ship the feature — it's to ship it using **four specific prompting tactics**, in order:

1. **Spec-first** — write `SPEC.md` *before* any code; resolve the open questions above; get Claude to confirm it's buildable
2. **Test-first** — commit a failing test that pins the contract from the spec, *before* implementing
3. **Adversarial** — ask Claude explicitly to find issues with its own plan or implementation
4. **Constraint-shaped** — at the end, re-prompt with hard constraints ("can you do this with one fewer entity?" / "remove three lines without breaking tests")

Visible tests check:
- `SPEC.md` exists with the required sections
- The history feature works (creating, updating, deleting all produce rows)
- A history endpoint returns rows newest-first

Hidden grading goes deeper: SPEC.md quality, that the spec actually addresses the open questions above, and that the implementation matches what the spec promised.

`SOLUTION_NOTES.md` is auto-generated by hooks — your prompt history shows whether you used the tactics. The hook script flags sessions that look like the tactics weren't used.
